How I work

I learn by building. A concept I have only read about does not stay; a concept I have implemented, broken and repaired does. Most of what I know about Doctrine, HTTP status codes or pipeline hazards came from something that did not work and had to be diagnosed.

That is also why the project pages on this site describe the problems as much as the results. A project that went perfectly teaches nothing and proves nothing.

  1. Identify the problem or the idea
  2. Understand the technologies involved
  3. Design a first solution
  4. Build a prototype
  5. Test it and find where it breaks
  6. Improve it
  7. Document what happened

The chain I want to understand

My goal is not to master one layer but to understand how they depend on each other. A vulnerability rarely lives inside a layer; it lives at the seam between two of them.

  1. Application
  2. Operating system
  3. Network
  4. Infrastructure
  5. Cloud
  6. Security

In practice this pushes me towards two roles: DevSecOps, where security is built into the development pipeline itself, and network and infrastructure administration, where it is built into the way systems are connected.
