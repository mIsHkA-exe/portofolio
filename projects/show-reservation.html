Show Reservation Platform

A ticketing application for live shows, built with Symfony

  • Backend and frontend contributor
  • Team of four, ESILV, 2025 to 2026
  • Web

Context

A team assignment: build a web platform where visitors can browse live shows, create an account, book a seat and review their past reservations, with an administration interface behind it.

The problem

Anything involving accounts raises the same question immediately: who is allowed to see what. A visitor browses. A logged-in user books and sees their own history. An administrator manages everything. Getting that wrong is not a display bug, it is a security hole.

Architecture

A Symfony MVC application: a MySQL database accessed through Doctrine ORM, Twig templates for the views, and controllers handling routes and requests. Administration routes are protected by role-based access control, so an authenticated user without the administrator role cannot reach them even by typing the URL.

  1. Create an account
  2. Log in
  3. Browse the available shows
  4. Book a seat
  5. Confirm the reservation
  6. Simulated payment step
  7. Review past reservations

My role

I worked across both sides of the application, contributing to the backend, including entity and database work and the controllers behind the reservation flow, and to the frontend templates that render it. Working on both ends made the connection between them concrete: a route resolves to a controller, which queries entities through Doctrine, and hands data to a Twig template that becomes the HTML the browser receives.

Working as a team

Four people on one codebase, splitting authentication, the home page, the reservation flow, database management and the administration features. This is where Git stopped being a command I ran and became something I actually needed: branches, merges, and the discipline of not breaking someone else's work.

Honest limitations

This is an academic beta. Payment is simulated, the application runs locally, and the data is for testing. Before anything like this could go live it would need automated tests, real payment integration, and a serious pass over access control and input validation.

What I took from it

  • Authorisation belongs on the server. Hiding a link in the interface hides nothing from someone typing the URL.
  • A shared codebase changes how you write. Code that only you can read is a problem, not a style.
  • Working across the full request cycle taught me more than either half would have alone.
